# Findings — narrative

This document accompanies `findings.csv`. The CSV is the canonical register; this file gives prose context for items where one-line evidence is insufficient.

## P0 highlights

### BE-SEC-001 — Broken RLS context manager

`backend/app/auth/dependencies.py:213-231` — `user_context_db(db, user_id)` is an `@contextmanager` that runs `SET LOCAL app.current_user_id = :user_id`. The dependency wires it like:

```python
def get_db_with_user_context(...):
    with user_context_db(db, user_id):
        pass  # context exits here
    return db   # session yielded with no active context
```

`SET LOCAL` is per-transaction. Once the `with` exits, the transaction either commits or is rolled back, and the setting is lost before the route handler ever issues a query. Any future RLS policies reading `current_setting('app.current_user_id')` will see NULL.

**Fix:** convert to an async generator dependency; yield the session inside the `with` so the transaction stays alive for the request's lifetime. Add a positive test asserting `current_setting('app.current_user_id', true)` is non-null inside a route, plus a cross-user data-leak negative test.

### BE-SEC-003 — Encryption fail-soft

`backend/app/services/encryption_service.py:36-55`:

```python
def encrypt(self, plaintext: str) -> str:
    try:
        return self._fernet.encrypt(plaintext.encode()).decode()
    except Exception:
        logger.warning(...)
        return plaintext  # silent plaintext

def decrypt(self, ciphertext: str) -> str:
    try:
        return self._fernet.decrypt(ciphertext.encode()).decode()
    except Exception:
        logger.warning(...)
        return ciphertext  # returns ciphertext as plaintext
```

Combined with `Account.plaid_access_token` (`backend/app/models/account.py:44-58`) using a `@property` that calls these, every Plaid token round-trip is a silent corruption candidate. In dev, where `SECRET_KEY` is generated fresh each restart (`config.py:186`), the previously-encrypted tokens become un-decryptable, and `decrypt` returns ciphertext. The next call to `encrypt` then runs the ciphertext through Fernet again — no error, but the data is now double-encrypted with a different key.

**Fix:** hard-fail on encryption error; raise a domain exception. Switch key derivation to HKDF with a per-tenant salt. Add a property-test (Hypothesis) for round-trip identity.

### BE-PERF-001 — Async route blocked on Celery .get()

`backend/app/routes/ml.py:60`: `result_async.get(timeout=30)`. This is a blocking call inside an `async def` handler. Under any ML latency, the FastAPI event loop is fully stalled. With `uvicorn --workers 1`, throughput collapses to ~1 req/s. Even with 4 workers, p99 latency on unrelated endpoints spikes during ML calls.

**Fix options:** (a) `loop.run_in_executor(None, result_async.get, 30)` — quick win; (b) submit the task and return `202 Accepted` with a job id, deliver the result over the existing WebSocket channel — preferred for production.

### FE-SEC-001 — WS token in querystring

`frontend/src/hooks/useWebSocket.ts:133`: `const url = \`${base}?token=${token}\`;`. The token ends up in:
- nginx access logs
- any upstream proxy logs
- browser referrer headers in some configurations

**Fix:** open the WebSocket without a token, then send the token as the first message after `accept()`. Server-side, gate all subsequent messages on a `state.authenticated` flag that flips only after token verification.

### ML-PR-001 — Optimization stack is dead code

`ml-worker/worker.py:38` initializes `production_orchestrator: Optional[ProductionOrchestrator] = None` and never assigns it. The `worker_ready` hook (`:71-113`) takes the "light startup" branch unconditionally because `_is_light_startup` (`:40-42`) always returns True. As a result:

- `OptimizedInferenceEngine` (caching, ONNX session, batched inference, thread pool, warmup) — never runs.
- `ABTestingFramework` — never runs.
- `ModelMonitoring` (Prometheus metrics on :8000) — never starts. **There is no `/metrics` endpoint anywhere.**
- ONNX FP32 + dynamic-q8 + static-q8 artifacts (~135 MB total under `ml_models/production/`) — generated by the background thread, never used.

The live path (`worker.py:154-165`) is plain PyTorch sentence-transformers. Per the user's confirmation, the resolution is to **revive** the orchestrator (Section F), since INT8 ONNX promises ~3-5x latency improvement on CPU.

### INFRA-CI-001 — `ci.yml` is 0 bytes

The repo has *no* CI. `ci.yml` is an empty file at the repo root. `.github/workflows/` does not exist. Combined with `scripts/check.sh:8,12` swallowing errors with `|| true`, no automated check has ever guarded the codebase.

**Fix:** author `.github/workflows/ci.yml` with stages: ruff/black/isort, mypy, pytest with `tests (per-package)`, vitest, playwright, docker build (incl. fixed frontend prod image), trivy scan, lighthouse-ci. Move it to `.github/workflows/audit.yml` as a final integration step.

### INFRA-DOCK-001 — Frontend production image cannot build

`frontend/Dockerfile:53` runs `COPY nginx.conf /etc/nginx/conf.d/default.conf`, but `frontend/nginx.conf` does not exist in the repo. The production target therefore fails at build. Since `docker-compose.yml:61` uses `target: dev`, this has been latent.

**Fix:** add `frontend/nginx.conf` with SPA history fallback (`try_files $uri /index.html;`), gzip, security headers, and cache rules for hashed assets.

## P1 themes

- **Schema drift** (BE-PR-001/002) — single Alembic revision, then `create_all` at startup. Future agents must produce a migration to head before any change to models.
- **No structured logs / observability** (BE-LOG-*, INFRA-OBS-*) — Section C is the single largest paving job.
- **Two of everything** (BE-PR-003/004, FE-PR-005, FE-LOG-002) — duplicate seeds, duplicate db modules, two query-key systems, two toast libs. Pick one each.
- **Dead Plaid webhook verification** (BE-SEC-006) — `PLAID_BASE_URL` referenced but undefined. Currently 500s on any real Plaid webhook.
- **Sync DB driver under async** (BE-PERF-002) — fundamental scalability ceiling. Decision needed: invest in async migration, or add executor wrapping as a stop-gap.

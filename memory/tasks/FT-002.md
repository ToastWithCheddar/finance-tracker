# TaskSpec: FT-002 — Transactions Create/Update Alignment

- ID: FT-002
- Purpose: Align Transactions create/update flows with backend contracts and use the adapter for response mapping; add `notify` support.

## Context
- Backend endpoints (prefix `/api/transactions`):
  - POST `` (Create) — supports query `notify?: boolean`, body `TransactionCreate`.
  - PUT `/{transaction_id}` (Update) — body `TransactionUpdate`.
  - POST `/bulk-delete` — body may be an array of UUIDs or an object depending on backend; keep current payload but ensure contract-aligned field name if specified by OpenAPI.
  - POST `/import` — multipart CSV upload; leave as-is.
- Adapter `frontend/src/api/adapters/transaction.ts` provides `toTransactionView(dto)`; use it to normalize responses.

## Files To Touch
- `frontend/src/services/transactionService.ts`

## Exact Changes
1) Create Transaction:
   - Ensure payload mapping uses contract fields:
     - If `transaction.transactionDate` is set, send `transaction_date` as `YYYY-MM-DD`.
     - Prefer sending `amount_cents` if the caller already provides it; otherwise allow `amount` + `transaction_type` if such usage exists.
   - Add optional query param `notify` (default true in UI callers is OK).
   - Map the response using `toTransactionView` before returning.

2) Update Transaction:
   - Ensure payload mapping for `transactionDate` → `transaction_date` when present.
   - Map the response using `toTransactionView` before returning.

3) Bulk Delete:
   - Keep current endpoint and payload but align with contract if OpenAPI specifies either `string[]` body or `{ transaction_ids: string[] }`.
   - Return value can remain as-is.

4) Do not modify list/stats/export in this task (covered by other tasks).

## Acceptance Criteria
- `createTransaction` and `updateTransaction` responses are adapted via `toTransactionView`.
- `notify` query param is supported on create (and may be used on update if backend accepts; otherwise skip).
- Type-check passes: `npm --prefix frontend run type-check`.
- Smoke passes: `./scripts/smoke.sh`.

## Pitfalls
- Keep date strings in `YYYY-MM-DD` format; do not send Date objects.
- Do not change method signatures (callers rely on them).
- Preserve existing error handling and cache invalidation behavior in `BaseService`.
